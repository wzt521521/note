## 分两种 socket，读懂「读就绪」的具体含义

代码里有两种完全不同的 socket，它们的「读就绪」场景完全不一样，分开看就清晰了。

### 1. 监听套接字（listenfd）的读就绪

`listenfd` 不负责传输数据，只负责接新连接。
它的「读就绪」= **已经有客户端完成了 TCP 三次握手，新连接在内核队列里排好队了，你调用 `accept()` 会立刻拿到新连接，不会阻塞等待**。

你可以理解成：

- `listenfd` 是酒店前台的接待位
- 客人（客户端）走完进门流程（三次握手），站到前台前等你登记
- 只要前台有人等，这个接待位就「就绪」了，你过去就能直接办理入住（`accept` 得到新的客户端 fd），不需要等客人来

对应代码里的逻辑：
当 `fd == listenfd` 且 `FD_ISSET` 为真，就说明有新连接在等，直接 `accept` 就行，不会卡住。

### 2. 客户端连接套接字（cfd）的读就绪

普通客户端 fd 是用来收发数据的。
它的「读就绪」= **客户端发的数据已经到达内核的接收缓冲区了，你调用 `recv()` 会立刻读到数据，不会空等**。

包含三种具体场景：

- 正常收到数据：缓冲区里有字节，`recv` 返回读到的字节数（>0）
- 对端正常关闭：客户端发了 FIN 包，`recv` 立刻返回 0，表示连接结束
- 连接出错：比如网络断开，`recv` 立刻返回 -1，通过错误码告知原因

这三种情况都叫「读就绪」—— 核心是**读操作不会阻塞**，至于读出来是什么结果，你读完才知道。


记录哪些连接需要监听和哪些已经就绪都是使用fd_set，所以有两个fd_set，一个用来标志哪些需要监听，一个用来标记哪些已经就绪。
select会查询传入的fd_set，然后把需要监听但暂未就绪的位改为0，就绪的位保持为1不变，之后就对这些仍为1的fd进行遍历处理。
所以要传入副本给select，防止select把需要监听但是暂未就绪的改为0；如果没有传副本，这些原本需要监听但是暂未就绪的就会被误以为无需监听了。

select 模型的核心性能问题：性能随总连接数线性下降，开销呈 O(n) 增长。其根源在于两层全量遍历：一是内核态需要逐个检查 0~maxfd 范围内所有 fd 的就绪状态并修改位图；二是用户态必须完整遍历 0~maxfd 才能筛选出就绪 fd。最突出的痛点是：哪怕连接处于完全空闲状态，只要在监听集合中，每一轮循环都会被完整检查一次，无效算力浪费随连接数同步增长。连接数越高，真正用于数据处理的算力占比越低。此外 select 还存在 FD_SETSIZE 硬上限（默认 1024），无法支撑大规模并发连接。、

poll的核心数组是vector<pollfd>，pollfd的结构大致如下：
struct pollfd {
    int      fd;      // 要监听的文件描述符（用户设置，永久不变）
    short    events;  // 你关心什么事件（用户设置，永久不变，比如POLLIN）
    short    revents; // 实际发生了什么事件（内核填写，每次poll刷新）
};
poll的核心改进在于突破了数量上的硬性限制和无需每轮遍历进行拷贝操作，可以直接修改原数组。poll同样有两轮遍历
第一轮遍历执行poll操作：
int nready = poll(pfds.data(), pfds.size(), 100);
主要工作是
1. **先全局重置**：遍历整个 pollfd 数组，把所有元素的 `revents` 全部清成 0，相当于统一标记为「本次暂未就绪」
2. **逐个检查状态**：遍历每个 fd，检查实际发生了什么事件
3. **写入就绪结果**：有事件发生的 fd，就把对应事件位（`POLLIN` / `POLLHUP` 等）写进它的 `revents` 字段
4. **返回就绪总数**

第二轮遍历：
第二轮是**用户态的全量遍历**，在 poll 系统调用返回之后执行 `for (size_t i = 0; i < pfds.size(); )` 循环，核心任务是**逐个读取每个元素的 revents 字段，筛选出本轮就绪的 fd 并对应处理**。

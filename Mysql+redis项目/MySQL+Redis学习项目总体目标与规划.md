# WSL 下 MySQL + Redis 学习项目：总体目标与实施规划

## 1. 项目定位

本项目面向 MySQL、Redis 和 Linux/WSL 初学者。目标不是一次性做出复杂产品，而是通过一个规模可控、能够逐步扩展的小型后端项目，理解以下三个问题：

1. 数据为什么要存入 MySQL？
2. Redis 能解决什么问题，哪些数据不应只放在 Redis 中？
3. 应用程序如何同时使用 MySQL 和 Redis，并在性能与数据正确性之间取得平衡？

建议项目名称：**Mini Blog（迷你内容社区）**。

核心业务包括：

- 用户注册、登录和查询；
- 发布、修改、删除和浏览文章；
- 给文章点赞；
- 查询文章浏览量；
- 查询热门文章排行榜；
- 使用 Redis 缓存高频查询；
- 对部分接口进行简单限流。

这套业务足够简单，适合独立完成，同时能自然覆盖关系型数据库、缓存、计数器、排行榜和缓存一致性等基础知识。

## 2. 总体学习目标

完成项目后，应能够独立说明并实践以下内容。

### 2.1 WSL 与 Linux 基础

- 理解 Windows、WSL 和 Linux 文件系统之间的关系；
- 能使用终端完成目录、文件、权限、进程、端口和日志等基本操作；
- 能安装、启动、停止和检查 MySQL、Redis 服务；
- 能判断端口占用、服务未启动、权限不足等常见问题；
- 能使用环境变量保存项目配置，避免在代码中写死密码。

### 2.2 MySQL 基础

- 理解数据库、表、行、列、主键、外键、索引和约束；
- 掌握增、删、改、查以及排序、分页、聚合和多表关联；
- 能根据业务设计用户表、文章表和点赞记录表；
- 理解事务及其在点赞、删除等业务中的作用；
- 会使用 `EXPLAIN` 初步分析查询；
- 理解索引可以加速查询，但也会增加写入和存储成本；
- 会进行数据库导出、恢复和基础故障排查。

### 2.3 Redis 基础

- 理解 Redis 是内存数据库，不是 MySQL 的简单替代品；
- 掌握 String、Hash、Set、Sorted Set 等常用数据结构；
- 理解键名设计、过期时间 TTL 和内存淘汰的基本概念；
- 能实现查询缓存、浏览量计数、点赞去重、热门排行榜和简单限流；
- 理解缓存穿透、缓存击穿、缓存雪崩和缓存一致性问题；
- 知道 Redis 数据丢失的可能性以及 RDB、AOF 的基本作用。

### 2.4 后端项目基础

- 能设计并实现一组 REST API；
- 能分离配置、数据访问、业务逻辑和接口层；
- 能正确处理参数校验、错误响应、日志和密码哈希；
- 能编写基础测试，并通过接口工具验证业务流程；
- 能用 README 说明项目的启动方式和设计思路。

## 3. 推荐技术方案

为降低入门难度，默认推荐以下组合：

- 运行环境：WSL 2 + Ubuntu；
- 后端语言：Python；
- Web 框架：FastAPI；
- MySQL：保存用户、文章、点赞关系等需要可靠持久化的数据；
- Redis：缓存、临时计数、排行榜和限流；
- 数据库访问：先使用原生 SQL 学习基础，再按需要引入 SQLAlchemy；
- 接口测试：浏览器自带的 Swagger 页面、curl 或 Postman；
- 版本管理：Git；
- 后期可选：Docker Compose。

如果你更熟悉 Java、Go、Node.js 或其他语言，可以替换后端语言和框架，但建议保留相同的业务目标与数据库设计。

初学阶段建议先直接在 WSL 中安装和运行 MySQL、Redis。等你能解释各服务如何工作后，再增加 Docker Compose；不要让容器配置掩盖数据库本身的学习重点。

## 4. 项目最终形态

### 4.1 核心功能

项目最终至少应支持：

1. 用户注册和登录；
2. 创建、查看、修改和删除文章；
3. 按时间分页查询文章列表；
4. 用户对文章点赞和取消点赞；
5. 记录并查询文章浏览量；
6. 查询热门文章排行榜；
7. 缓存文章详情，并在文章变更后正确处理缓存；
8. 对登录或文章详情接口进行简单限流；
9. 提供数据库初始化脚本、配置示例和启动说明；
10. 提供少量自动化测试或可重复执行的接口测试步骤。

### 4.2 建议架构

```text
客户端 / Swagger / curl
          |
          v
      FastAPI 应用
       /        \
      v          v
   MySQL       Redis
 持久化数据   缓存与临时数据
```

建议坚持一条原则：**MySQL 是业务事实的主要来源，Redis 是加速器和临时状态存储。**

例如，文章正文必须保存在 MySQL 中；文章详情可以缓存在 Redis 中。Redis 缓存丢失后，系统仍应能够从 MySQL 恢复正常服务。

## 5. 数据模型初稿

以下结构只作为设计起点。正式建表前，应自己思考字段类型、长度、默认值和索引。

### 5.1 用户表 `users`

- `id`：主键；
- `username`：用户名，唯一；
- `password_hash`：密码哈希，禁止存储明文密码；
- `created_at`：创建时间；
- `updated_at`：更新时间。

### 5.2 文章表 `posts`

- `id`：主键；
- `user_id`：作者 ID；
- `title`：标题；
- `content`：正文；
- `status`：文章状态，可选；
- `created_at`：创建时间；
- `updated_at`：更新时间。

### 5.3 点赞记录表 `post_likes`

- `id`：主键，或者使用联合主键；
- `user_id`：点赞用户 ID；
- `post_id`：文章 ID；
- `created_at`：点赞时间；

应通过唯一约束保证同一用户不能重复点赞同一文章。

### 5.4 Redis 键设计示例

| 用途 | 建议键名 | 数据结构 | 说明 |
|---|---|---|---|
| 文章详情缓存 | `post:detail:{post_id}` | String 或 Hash | 设置合理 TTL |
| 文章浏览量 | `post:views:{post_id}` | String | 使用原子自增 |
| 用户点赞集合 | `post:likers:{post_id}` | Set | 用于去重练习 |
| 热门文章榜 | `rank:posts:daily` | Sorted Set | 分数可由浏览或点赞产生 |
| 接口限流 | `rate:user:{user_id}:{window}` | String | 自增并设置过期时间 |

注意：为了练习数据一致性，点赞的最终记录仍建议保存在 MySQL 中。Redis 中的点赞集合可以作为查询加速或学习实验，但不能在没有持久化方案时成为唯一数据来源。

### 阶段 3：引入 Redis 文章缓存

> 完成状态：✅ 已完成（2026-09-12）。文章详情缓存、TTL 与空值缓存、写后失效、命中统计及 Redis 故障降级均已验证；可重复验收步骤见 MiniLog 项目的 `docs/stage3-verification.md`。

学习内容：

- Redis 常见数据结构和 TTL；
- Cache Aside（旁路缓存）模式；
- 缓存命中与未命中；
- 更新数据库后删除缓存；
- 缓存空值，缓解缓存穿透；
- 为 TTL 加少量随机值，降低同时过期风险。

建议读取流程：

```text
查询文章详情
  -> 先查 Redis
  -> 命中：返回缓存
  -> 未命中：查询 MySQL
  -> 写入 Redis，并设置 TTL
  -> 返回结果
```

建议更新流程：

```text
修改或删除文章
  -> 先更新 MySQL
  -> 成功后删除对应 Redis 缓存
```

阶段产出：

- 文章详情缓存；
- 缓存命中、未命中的日志或统计；
- 文章修改、删除后的缓存失效逻辑；
- Redis 临时不可用时的降级处理。

验收标准：

- 首次查询来自 MySQL，随后相同查询能够命中缓存；
- 修改文章后不会长时间读取到旧内容；
- 删除文章后缓存中不会继续返回文章；
- 暂停 Redis 后，文章详情仍可以从 MySQL 获取，而不是整个接口崩溃。

## 7. 建议接口清单

接口路径可以自行调整，重点是保持语义清晰。

| 方法 | 路径 | 功能 | 主要存储 |
|---|---|---|---|

## 10. 每个阶段的固定学习循环

建议对每个功能使用同一套循环：

1. **先设计**：写出请求、响应、数据表和异常情况；
2. **先做最小版本**：只实现正确的基本流程；
3. **手动验证**：使用 SQL 客户端、Redis CLI 和接口工具观察真实数据；
4. **故意制造错误**：停止服务、重复请求、输入非法参数、删除缓存；
5. **补充测试**：把已经验证的关键场景固化下来；
6. **记录理解**：说明为什么使用 MySQL、为什么使用 Redis；
7. **提交 Git**：每次提交只包含一个相对完整的学习目标。

每个阶段建议回答以下问题：

- 数据最终存在哪里？
- 如果 Redis 中的数据全部丢失，系统会怎样？
- 如果 MySQL 暂时不可用，系统会怎样？
- 当前操作是否需要事务？
- 当前缓存何时创建、何时过期、何时删除？
- 如何证明功能正确，而不只是“看起来能运行”？

## 11. 必做实验

这些实验比单纯完成接口更有学习价值。

### 实验 1：观察缓存命中

1. 删除某篇文章的 Redis 缓存；
2. 第一次请求文章详情，观察 MySQL 查询；
3. 第二次请求同一文章，观察缓存命中；
4. 比较两次请求的日志和耗时。

### 实验 2：验证缓存一致性

1. 请求文章详情，使其进入缓存；
2. 修改文章；
3. 再次查询详情；
4. 确认返回的是新内容；
5. 分析如果忘记删除缓存会发生什么。

### 实验 3：验证数据库约束

1. 连续执行两次相同用户对相同文章的点赞；
2. 观察应用层响应；
3. 直接检查数据库；
4. 确认唯一约束仍能守住最后一道防线。

### 实验 4：模拟 Redis 故障

1. 暂停 Redis；
2. 请求文章详情；
3. 观察系统是否回退到 MySQL；
4. 请求热门榜单；
5. 记录哪些功能可以降级，哪些功能会暂时不可用。

### 实验 5：模拟 MySQL 故障

1. 暂停 MySQL；
2. 分别请求已缓存和未缓存的文章；
3. 尝试创建文章；
4. 观察并记录错误处理；
5. 思考缓存命中时是否应该返回数据，以及数据可能有多旧。

### 实验 6：索引对比

1. 准备一定数量的测试文章；
2. 对常用查询执行 `EXPLAIN`；
3. 添加合适索引；
4. 再次执行并比较执行计划；
5. 记录索引对查询和写入的影响。

### 实验 7：备份与恢复

1. 创建一些测试数据；
2. 导出数据库；
3. 将备份恢复到另一个测试数据库；
4. 比较表结构与核心数据；
5. 将完整过程写入项目文档。

## 12. 常见误区与边界

- 不要将明文密码写入数据库、代码、Git 提交或日志；
- 不要使用 `KEYS *` 作为生产式查询方案，学习阶段也应知道其风险；
- 不要给所有字段都建立索引，应根据查询模式设计；
- 不要为了使用 Redis 而缓存所有接口；
- 不要把 Redis 当成绝对可靠的唯一数据源，除非已经专门设计持久化与恢复方案；
- 不要在一次请求中无节制地进行大量数据库查询；
- 不要只测试正常输入，也要测试重复、空值、越权、超长文本和服务故障；
- 不要一开始就引入消息队列、微服务、分布式锁等过多概念；先完成单体项目并理解数据流。

## 15. 最终复盘问题

完成项目后，尝试不查资料回答：

1. 为什么文章数据应该以 MySQL 为主，而不是只存在 Redis？
2. 缓存命中、缓存未命中和缓存失效分别是什么意思？
3. 修改文章后为什么通常删除缓存，而不是同时直接更新缓存？
4. 如何防止同一用户重复点赞？
5. 哪些操作需要事务，为什么？
6. Redis 的 String、Set、Sorted Set 在本项目中分别解决了什么问题？
7. Redis 宕机后哪些功能必须继续可用？
8. 索引为什么能加速查询，又为什么不能越多越好？
9. 如何证明一次性能优化确实有效？
10. 如果让另一个人接手项目，他需要哪些文档？

如果这些问题大部分都能结合自己的代码、日志和测试结果回答，而不是只背诵定义，就说明你已经达到了这个项目的核心学习目标。

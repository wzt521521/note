先把 `ReplicationGraph`、`ActorChannel` 这些名字都忘掉。

空间格子的本质只有一句话：

> 把地图分成很多小区域，服务器先看玩家在哪个区域，然后只同步附近的人。

## 例子：没有空间格子

地图里有100名玩家。

玩家1连接服务器后，服务器要判断：

```text
玩家2要不要同步给玩家1？
玩家3要不要同步给玩家1？
玩家4要不要同步给玩家1？
……
玩家100要不要同步给玩家1？
```

玩家1需要检查99个人。

100名玩家都这样检查，大约就是：

```text
100 × 99 = 9900次关系检查
```

即使玩家1在地图左边，玩家100在地图最右边，服务器也要先检查距离，才能知道“不需要同步”。

## 使用空间格子

假设地图是400米×400米。

我们把它分成16个100米×100米的格子：

```text
┌──────┬──────┬──────┬──────┐
│ 格子1 │ 格子2 │ 格子3 │ 格子4 │
├──────┼──────┼──────┼──────┤
│ 格子5 │ 格子6 │ 格子7 │ 格子8 │
├──────┼──────┼──────┼──────┤
│ 格子9 │格子10│格子11│格子12│
├──────┼──────┼──────┼──────┤
│格子13│格子14│格子15│格子16│
└──────┴──────┴──────┴──────┘
```

服务器会记录：

```text
格子1：玩家1、玩家2、玩家3
格子2：玩家4、玩家5
格子3：没有玩家
格子4：玩家6、玩家7
……
```

现在玩家1位于格子1。

服务器不再检查地图里的99名玩家，而是直接找到：

```text
格子1：玩家1、玩家2、玩家3
```

那么服务器只需要重点考虑：

```text
玩家2
玩家3
```

其他很远的玩家，连距离判断都可以省掉。

## 玩家移动时怎么办

假设玩家3原来在格子1：

```text
格子1：玩家1、玩家2、玩家3
格子2：玩家4、玩家5
```

后来玩家3跑进格子2。

服务器就更新一下记录：

```text
格子1删除玩家3
格子2添加玩家3
```

更新后：

```text
格子1：玩家1、玩家2
格子2：玩家3、玩家4、玩家5
```

所以空间格子需要做两件事：

```text
1. 玩家移动时，更新玩家属于哪个格子
2. 给客户端同步时，只取客户端附近格子的玩家
```

## 站在格子边缘怎么办

这是一个很重要的问题。

假设格子边界在100米的位置：

```text
玩家A位置：99米
玩家B位置：101米
```

画出来就是：

```text
格子1             格子2
─────────│─────────
 玩家A   │ 玩家B
  99米   │ 101米
```

虽然他们属于两个不同格子，但实际上只相距2米，肯定应该互相看见。

一种简单方案是：

```text
客户端查询自己格子，以及周围的格子
```

例如玩家A在格子1，就查询：

```text
格子1
格子2
周围其他相邻格子
```

而 UE 的空间格子主要采用另一种方法：

> 一个玩家可以登记到多个格子里。

例如玩家B的网络可见距离是50米，那么玩家B不仅登记在格子2，也登记到旁边的格子1：

```text
格子1的名单：玩家A、玩家B
格子2的名单：玩家B
```

注意，这不是创建了两个玩家B。

只是两个格子的名单中，都保存了“玩家B的地址”：

```text
格子1 → 玩家B指针
格子2 → 玩家B指针
```

因此玩家A查询格子1时，仍然能够找到玩家B。

## 和带宽有什么关系

假设没有格子时，玩家1需要接收附近20名玩家的信息，但服务器一开始不知道哪20名在附近。

于是服务器可能先检查99名玩家：

```text
检查99人
找到附近20人
发送这20人的数据
```

使用格子以后：

```text
直接从格子名单中拿到附近大约20人
发送这20人的数据
```

节省的主要是：

```text
不用遍历远处的79人
不用给远处玩家准备复制数据
不用维持大量不必要的ActorChannel
减少属性比较
减少服务器CPU消耗
减少内存和带宽
```

## 和 ActorChannel 的关系

可以把 `ActorChannel` 理解为：

> 服务器与某个客户端之间，专门用来同步某个 Actor 的通信档案。

例如玩家1能看见玩家2：

```text
玩家1的连接
    ↓
玩家2的ActorChannel
    ↓
同步玩家2的位置、血量、动画状态
```

如果玩家1附近只有20个人，服务器主要维持这20个人的同步关系。

如果完全不做空间筛选，服务器可能需要面对更多“连接—Actor”关系。

所以空间格子做的事情是：

```text
先找出附近Actor
    ↓
再为这些Actor进行网络复制
    ↓
需要时创建或维持ActorChannel
```

## 但有一种情况格子没用

如果100名玩家全部挤在一个房间：

```text
同一个格子：
玩家1、玩家2、玩家3……玩家100
```

那么玩家1查询这个格子，仍然会拿到另外99个人。

这时依然接近：

```text
100 × 99 = 9900
```

所以空间格子最适合：

```text
地图比较大
玩家分布比较散
远处玩家不需要同步
```

## 用一句话总结完整流程

假设客户端A进入服务器：

```text
1. 服务器取得客户端A的观察位置
2. 根据位置算出A在哪个格子
3. 从这个格子的名单中取出附近Actor
4. 加上GameState等全局Actor
5. 加上A自己的PlayerController等私有Actor
6. 对这些Actor进行属性同步
7. 其他远处Actor暂时不发给A
```

你可以把它想象成外卖配送：

```text
没有格子：
在全市100家店里逐个寻找附近的店

有格子：
先确定你属于哪个商圈，只查看这个商圈的店
```

空间格子优化的不是“发送数据的方法”，而是：

> 在发送之前，快速找出这个客户端究竟需要关心哪些 Actor。

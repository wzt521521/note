我认为，UE5 这套网络架构最值得学习的，并不是 `OutRec`、`InRec` 或 ACK/NAK 本身，而是它背后的一个设计思想：

把“数据怎么运输”“哪些消息必须可靠”“哪些数据只需要最新状态”“不同对象之间是否需要相互等待”这几个问题拆开解决。

它不是一套单纯追求可靠性的网络协议，而是一套为实时多人游戏设计的、在可靠性、实时性和带宽之间做权衡的系统。

下面还是从你已经理解的 `NetConnection → Packet → Channel → Bunch` 来分析。

# 一、最大的亮点：不是所有数据都值得可靠传输

假设你在开发一款多人射击游戏，服务器每秒需要同步：

| 数据      | 需要每次都收到吗？   | 适合的机制               |
| ------- | ----------- | ------------------- |
| 玩家坐标    | 不需要，最新位置更重要 | 状态复制                |
| 玩家血量    | 不需要每个中间值    | 属性复制                |
| 开门事件    | 可能需要每次可靠执行  | Reliable RPC        |
| 播放枪口火焰  | 偶尔丢失可接受     | Unreliable RPC      |
| 购买物品的确认 | 需要可靠处理      | Reliable RPC + 业务校验 |

例如玩家位置从 A 移动到 B，再移动到 C：

```
服务器：

位置 A → 位置 B → 位置 C

客户端：

位置 A ─────────→ 位置 C
```

位置 B 丢失了，有必要强制重传吗？

没有必要。

因为当客户端已经能够得到位置 C 时，再去应用过时的位置 B，反而可能增加延迟并产生不理想的视觉效果。

但是，如果服务器发送了两条重要事件：

```
RPC1：购买一把武器
RPC2：装备这把武器
```

这两条 RPC 的执行顺序可能非常重要。

所以 UE5 同时提供：

- 事件可靠性：Reliable RPC 保证相应可靠调用按规定顺序送达。
- 状态收敛性：属性复制允许丢弃中间状态，持续复制最新需要同步的状态。

这两种机制不是彼此替代的，而是分别解决不同类型的问题。

# 二、第二个亮点：把可靠顺序限制在 Channel 内，而不是整个连接

这可能是四层架构中最值得你深入研究的地方。

假设一个 NetConnection 有两个 Channel：

```
NetConnection
    |
    ├── Channel 4（玩家 A）
    |
    └── Channel 9（玩家 B）
```

现在服务器发送：

```
Packet 100
├── Channel 4：Reliable R7（玩家 A 换武器）
└── Channel 9：位置 B1

Packet 101
├── Channel 4：Reliable R8（玩家 A 开火）
└── Channel 9：位置 B2
```

假设 Packet 100 丢失，Packet 101 正常抵达。

Packet 100 丢失后的客户端处理

Channel 4

R8 必须等待 R7

保证同一个 Channel 内可靠消息的顺序

Channel 9

B2 可以处理

不必等待 Channel 4 的 R7

示意前提：B2 是有效的新状态更新，不依赖其他缺失的可靠初始化消息。

如果我们使用一个全局有序的可靠字节流，例如单条 TCP 连接，在 Packet 100 对应的数据缺失时，后续字节即使已经到达，也必须等待缺失部分补齐之后才能按序交给应用。

这叫 Head-of-Line Blocking（队头阻塞）。

UE5 的 Channel 设计允许可靠消息在各自的 Channel 中维护顺序，从而避免把同一个可靠消息缺口变成整个连接所有 Actor 的应用层顺序依赖。

需要注意，这并不是说不同 Channel 在带宽和拥塞上完全独立。它们仍共享 NetConnection 和底层网络资源。

真正的亮点在于：把“可靠消息的顺序约束”从连接级缩小到了业务 Channel 级。

# 三、第三个亮点：传输单位与可靠性单位分离

你之前一直在追问：

> 为什么 Packet 丢失后，不直接重传 Packet，而要到 Channel 的 OutRec 中找 Bunch？

现在可以从架构设计的角度来回答。

因为 UE5 将两个不同的问题交给了两个不同层次：

| 层次                       | 核心问题            |
| ------------------------ | --------------- |
| NetConnection / Packet   | 哪一次网络发送丢失了？     |
| Channel / Reliable Bunch | 哪一条可靠业务消息还需要送达？ |

假设：

```
Packet 100
├── R7（Reliable）
└── U1（Unreliable）
```

Packet 100 丢失。

如果直接重传整个 Packet，那么：

```
重新发送 Packet 100 的内容
├── R7（需要）
└── U1（不需要）
```

这样会把没有重传需求的数据也一起发送出去。

UE5 的做法是：

```
Packet 100 NAK
        |
        v
查找相关 Channel
        |
        v
找到 OutRec 中的 R7
        |
        v
构造新的 Packet 105
        |
        v
只重传可靠 Bunch R7
```

这里还有一个更深层次的设计价值：

一次发送行为与一条业务消息的身份相互独立。

- `PacketId` 标识一次发送。
- `ChSequence` 标识所属 Channel 上的可靠消息顺序。
- 同一个 R7，可以先出现在 Packet 100，再出现在 Packet 105 中。

这样就允许 Packet 继续负责高效率的数据打包，而 Channel 独立负责可靠消息的生命周期。

这其实是一种很典型的软件架构思想：关注点分离（Separation of Concerns）。

# 四、第四个亮点：在 NetConnection 层集中打包，提高网络利用率

假设一帧内有 100 个 Actor 需要同步，每个 Actor 的数据只有几十字节。

如果每个 Channel 都自己发送 UDP 数据报，就可能产生大量小包。

每个 UDP/IP 数据报都存在协议头及其他处理开销，因此大量小包通常不划算。

UE5 的设计允许不同 Channel 的 Bunch 汇入同一个连接的发送缓冲：

```
Channel 1 → Bunch A ──┐
Channel 2 → Bunch B ──┤
Channel 3 → Bunch C ──┼──→ NetConnection
Channel 4 → Bunch D ──┘           |
                                 v
                            SendBuffer
                                 |
                                 v
                             Packet 100
```

这里要注意：

Channel 负责生产要发送的逻辑消息，NetConnection 负责把多条逻辑消息组织成物理网络传输。

因此，架构既保留了按 Actor/Channel 组织业务数据的灵活性，又不需要为了每条业务消息单独产生一个网络 Packet。

当然，实际 UE5 的打包还受到 MTU、最大 Packet 大小、发送策略和 PacketHandler 等因素影响，并不是所有 Bunch 都一定能放进同一个 Packet。

# 五、第五个亮点：把带宽分配当成游戏逻辑的一部分

这是 UE5 网络架构在工程应用中非常有价值的一层。

假设服务器有 1000 个 Actor，但某个客户端只能看到其中 50 个，而且网络带宽有限。

服务器不应该平等地向客户端发送这 1000 个 Actor 的状态。

UE5 的传统 Actor 复制体系有几个重要概念：

- `Relevancy`：这个 Actor 是否与客户端相关？
- `NetPriority`：在带宽有限时，哪个 Actor 应该优先同步？
- `NetUpdateFrequency`：这个 Actor 需要多频繁地考虑更新？
- `Dormancy`：这个 Actor 是否可以暂时停止频繁参与复制检查？

官方文档明确指出，带宽受限时 UE 会按 Actor 的复制优先级进行资源分配，而不是保证所有 Actor 在每一轮网络更新中都被复制。

例如，靠近玩家、正在交战的 Actor 可能比远处静止的装饰性 Actor 更值得优先同步。

# 六、这些设计不是没有代价

我们可以把几个收益和代价放到一起看。

| 设计选择                     | 收益                | 代价                             |
| ------------------------ | ----------------- | ------------------------------ |
| Reliable 与 Unreliable 并存 | 兼顾可靠性与实时性         | 开发者需要正确选择                      |
| 每个 Channel 独立维护可靠顺序      | 减少跨 Channel 的顺序阻塞 | 同一 Channel 仍会阻塞                |
| Packet 与 Bunch 分离        | 只重传需要可靠送达的数据      | ACK、ChannelRecord、OutRec 管理更复杂 |
| 属性按状态复制                  | 节约带宽，避免执着于旧状态     | 中间变化可能被跳过                      |
| 多 Channel 汇聚 Packet      | 降低小包开销            | 需要打包和分片处理                      |
| Actor 优先级及相关性            | 有限带宽用于重要对象        | 状态更新可能被延后                      |

特别是 Reliable RPC，不能因为它可靠就频繁发送。

如果同一 Channel 的可靠消息不断堆积，之前的消息迟迟无法被确认，后续可靠消息就可能持续等待，而且可靠缓冲也会产生压力。Epic 官方也提醒避免在高频输入中滥用 Reliable RPC。

# 七、从架构角度重新理解这四个对象

我建议你把它们看成四个相互配合的角色，而不是简单的四个嵌套对象。

NetConnection：传输与调度管理者

负责连接级 Packet 组织、发送、确认和丢失判断。

Channel：逻辑消息流管理者

负责所属消息的可靠顺序、OutRec、InRec，以及相关 Actor 的消息处理。

Bunch

逻辑消息

回答：这次传输什么数据？是否可靠？

Packet

网络传输单元

回答：这次怎样把数据送出去？

这是职责上的分层示意，并不是严格的对象继承或包含关系。

## 最后，我认为最值得借鉴的设计原则

如果要用一句话总结：

UE5 没有让所有网络消息都遵循同一套可靠、有序、必须送达的规则，而是把这些保障拆开，按业务需求应用在最合适的层次。

它所追求的不是“网络上绝不丢失任何数据”，而是：

> 在网络延迟、丢包和有限带宽的现实条件下，尽量及时地呈现重要状态，并确保真正不能丢失的业务消息得到可靠处理。

这里讨论的主要是 UE5 传统 `UNetConnection / UChannel / Bunch` 复制路径；现代 Iris 复制系统的部分内部组织方式有所不同。

如果继续深入，我认为下一步最有价值的问题是：

既然 UE5 的可靠 Bunch 按 Channel 独立维护，那么一个 Channel 的 OutRec 堆积、丢包重传，究竟在什么条件下会影响同一个 NetConnection 里的其他 Channel？

这个问题能把你对可靠顺序、连接带宽、发送缓冲以及队头阻塞的理解真正联系起来。

示例问题 2：你项目里最复杂的技术问题是什么？如果现在重新做，你会怎么改进？
考察目的：不是单纯问你遇过什么困难，而是看你能否复盘方案的不足、分析设计取舍，以及有没有技术成长。


演进过程，首先是考虑完美的实现，通过一个结构体，不断的记录每个角色的这帧的骨骼位置和旋转状体，希望在回退的时候，把每个玩家都进行回退，这引出了问题，1.我必须高度依靠UE提供的api，让ai指导我怎么去用这些api接口把角色移动回当时的世界坐标和进行骨骼的旋转，这引出了问题，第一，每个具体的骨骼旋转我是无法操控的，也就是我无法完美的在服务器上还原当时的世界状态，第二，这个回退会带来大量的计算开销，如果多个玩家同时开火，则服务器要不断的对当前的世界进行移动，这很可能会出现问题，所以我在思考后，决定寻找其他的解决方法，然后我主要是针对降低计算开销这方面进行了思考，因为在我看来，繁琐的计算开销是非常难以接受的，所以我想到了，可以降低精准性但是提高性能的数学方法，自己建立一个虚拟的数学世界坐标，让开火在这个世界里面进行检测运算，通过SSR里面的log日志，来判断是否真的能够击中目标，这在当时的我看来，是一个非常漂亮的实现，以很小的开销达到了SSR的目的，代价就在于不够精准。如果现在重新做，我更加倾向于用链表来进行每帧的玩家管理，这样的话提供更高的灵活性

示例问题 4：假设玩家网络延迟达到 150ms，出现了明明打中敌人却没有造成伤害的情况，你怎么分析和解决？
考察目的：考察你对延迟、客户端预测、服务器权威判定、延迟补偿及公平性的理解，而不是只要求知道一个技术名词。

我首先会确认150ms是RTT还是单程延迟。如果是RTT，服务器实际需要回退的大约是75ms，应该在现有SSR窗口内。因此我不会直接扩大回退时间，而是给每发子弹增加ShotId，沿着“RPC到达、服务器校验、时间对齐、历史帧选择、数学命中、墙体遮挡、伤害结算”逐段记录结果，确定子弹在哪一步丢失。


示例问题 5：假设现在你的项目从支持 5v5 变成支持 100 人同时对战，你认为主要瓶颈在哪里？
考察目的：系统性分析服务器 CPU、网络带宽、状态复制、Actor 数量、网络相关性、更新频率等因素，而不是立即给出一个优化方案。

第一，人数扩大了10倍，但是连接扩大了近100倍，这说明了连接的传递是指数级增长的，在一个小的地图里，可能这100个人的每个人的同步都会被互相传递，对于移动的复制以及碰撞的处理，这是一个很大的服务器网络负担，服务器不光要兼顾每个客户端的移动，还要进行网络的分发，以及碰撞等游戏逻辑的纠正，再加上我自己的SSR系统，每个人开枪，会针对每个玩家都做一次数学处理，那么在100个人都高频开火的前提下，每个人的每颗子弹都要对每个玩家进行一次解析处理，而且每帧服务器都要记录当前的游戏玩家状态，这样下来，服务器会承担非常大的开销。同理，客户端也难以承载100个人的场景下，大量的特效开销等等。

关于内存问题，服务器要有对其他玩家的连接connection，那么当连接变多时，服务器要为每个玩家都维护一套连接状态信息，100人就是要维护100套，这部分是线性增长必需的，但是每个connection下面都有channel，如果玩家互相相关，那么每条连接下面的channel数量会变的非常多，每个channel都要维护一套网络状态，这就需要高昂的内存，解决思路还是空间格子划分

解决思路有一种通用的，就是在服务器达到某个阈值的时候，降低网络更新的频率，简化角色的战斗表现，在业务层要尽可能的减少reliable。
排查问题首先要看具体的情况：
要看看在什么情况下会导致服务器出现瓶颈，具体是什么方面出现瓶颈，具体是什么原因导致的，看看服务器的带宽，服务器的内存，看看占比怎么样，这样才能定位到具体的问题
首先是自己的业务优化，SSR应该要用性能高的数据结构，同时要注意标记空间距离，通过空间距离来进行玩家筛选，避免每次都遍历所有玩家
然后就是引入空间格子，每个客户端只订阅自己附近的格子，只同步附近的玩家和actor状态，同时按照距离调整更新频率，近距离的玩家应该高频更新等等

问题 7：如果你的游戏现在需要加入登录、匹配、房间创建和战绩保存，你会如何设计服务器架构？
主管可以通过这个问题看出，你能否从一个 UE 游戏项目出发，扩展到更完整的在线游戏服务系统。

直白地说，我会把系统分成三部分：
1. 大厅服务器：负责登录、匹配、创建房间。
2. 游戏服务器：负责玩家真正打比赛。
3. 数据库：保存账号和战绩。
1. 登录
玩家输入账号密码。
客户端把账号密码发给大厅服务器，大厅服务器验证成功后返回：
PlayerId = 10001
LoginToken = abc123
以后玩家匹配、创建房间时都要携带这个 Token。
这样玩家身份由服务器确认，不能像当前 Demo 一样由客户端自己提交一个 GUID，否则客户端可以冒充别人。
2. 匹配
玩家点击“开始匹配”，大厅服务器把他放进队列：
玩家A：爆破模式，华东区
玩家B：爆破模式，华东区
玩家C：爆破模式，华东区
玩家D：爆破模式，华东区
人数足够后，大厅服务器：
1. 创建一个房间；
2. 找一台空闲的 Dedicated Server；
3. 把这四名玩家放进房间；
4. 把服务器 IP、端口和进入凭证发给他们。
例如：
RoomId = 8001
Server = 192.168.1.10:7777
JoinToken = xyz456
客户端拿到这些信息后，连接这台游戏服务器。
3. 创建房间
创建房间和匹配差不多。
区别只是：
- 匹配：系统自动找玩家并创建房间；
- 创建房间：玩家自己设置地图、模式、人数，其他玩家通过房间号加入。
房主只是修改房间配置，房主的电脑不负责权威计算。真正开局后，所有玩家仍然连接 Dedicated Server。
4. 开始比赛
玩家连接 Dedicated Server 时，要提交 JoinToken。
游戏服务器检查：
- Token 是不是真的；
- 玩家是不是这个房间的人；
- 房间有没有满；
- Token 有没有过期。
通过后才允许进入。
比赛中，伤害、血量、经济、击杀和胜负都由 Dedicated Server 决定，不能相信客户端上报的结果。
5. 保存战绩
比赛结束后，Dedicated Server 生成结果：
MatchId = 8001
玩家A：10杀5死
玩家B：6杀8死
获胜方：TeamA
然后把结果交给后台，后台写入数据库。
这里必须保证：
- 客户端不能自己提交战绩；
- 同一场比赛重复提交不能重复加分；
- 数据库暂时不可用时可以稍后重试；
- 写战绩不能卡住游戏线程。

问题 8：你觉得游戏服务端开发和普通互联网后端开发最大的区别是什么？
这个问题可能考察你的职业方向是否清晰，以及你是否理解实时战斗与游戏后台的不同技术需求。
你可以重点思考三个维度：实时性要求、状态一致性与公平性、不同业务模块的稳定性和扩展需求。

最大的区别是运行模型不同。普通互联网后端通常是请求驱动的，收到请求后完成一次业务处理；游戏服务端则需要维护长连接，并按照 Tick 持续模拟一个权威游戏世界。它对延迟和帧时间更加敏感，而且保存了大量房间内状态，因此不能像无状态 Web 服务一样随意切换实例。与此同时，游戏客户端不可信，服务器还要实时验证移动、射击、伤害和经济。登录、商城和战绩仍然采用传统后端的事务设计，而实时战斗部分更关注低延迟、状态同步和服务器权威。

问题 10：线上某个游戏服务器突然 CPU 占用率很高，玩家反馈卡顿，你会怎么定位？
看的是 Linux 基础、性能分析、日志排查、线程分析、网络指标，以及排查问题时的优先级判断。
这类问题的特点是：
以前可能问“什么是锁”“什么是网络 IO”；现在则可能问“你会在哪里使用锁”“这里为什么会出现性能瓶颈”。

我不会只看总 CPU，而是按照机器、进程、线程、函数和触发条件逐层缩小范围。首先将异常实例摘出匹配并保留现场，然后通过每核占用、服务器帧时间和 Unreal Insights 确定是 GameThread、网络线程还是后台任务。接着用 CPU 火焰图找到热点函数，并结合玩家数、Actor数、RPC速率和比赛阶段判断是单次计算变慢还是调用次数失控，最后在相同负载下验证修复效果。

本次讨论基于现代linux的主流方案，为了简化模型，选择性忽略一些细节处理。

1.外部碎片和内部碎片
2.真实内存和虚拟内存

关于1和2，二者是有强相连关系的，一个真实的free碎片，在真实内存来看，可能是内部碎片，在虚拟内存来看，可能是外部碎片，因此需要区分这个概念

首先需要建立进程的虚拟内存视角模型
在linux里面，进程往往是基于二进制文件运行，在这里，我们简化为二进制文件是一个CPP文件，这个CPP文件经历了
1.预处理（#define ,#include）
2.编译(constexpr以及语法检查等等)
3.链接（动态库.so和静态库.a）
然后被处理成ELF的文件格式，代表可执行文件，然后被选中执行，这个CPP最终生成的ELF被执行，生成了一个进程，这个进程的虚拟内存视角入如下：

现在的问题是，必须区分，这个进程的虚拟内存模型有很多类，这些类分别是怎么来的

```text
ELF 文件
├─ ELF Header
│  └─ 整个 ELF 的总说明：类型、架构、入口地址、Program Header 在哪里、Section Header 在哪里
├─ Program Header Table
│  └─ 描述 Segment：运行时哪些文件内容映射进内存、地址、大小、权限等
├─ 各种 Section 内容
│  ├─ .text       机器指令
│  ├─ .rodata     只读常量
│  ├─ .data       已初始化的全局/静态数据
│  ├─ .bss        未初始化或零初始化的全局/静态数据
│  ├─ .symtab     完整符号表
│  ├─ .strtab     .symtab 等使用的字符串表
│  ├─ .dynsym     动态符号表
│  ├─ .dynstr     动态符号使用的字符串表
│  ├─ .dynamic    动态链接信息
│  ├─ .rela.*     重定位信息
│  └─ 其他 Section
└─ Section Header Table
   └─ Section 的目录：每个 Section 的名字、位置、大小、类型、属性等
```

最重要的第一层认知是：ELF Header 是总目录；Section 是文件内部按“功能”组织的数据；Section Header Table 是这些 Section 的目录；Program Header Table 则是操作系统加载程序时使用的视图。

在ELF文件的内部构造里面，我们发现，BSS,DATA,TEXT,RODATA，全部都已经存在了，也就是意味着，在执行进程的初始化的时候，这些虚拟内存就已经被初始化了，而剩下的Heap，mmap，stack，更多的来自运行阶段的内存产生。

下面我重点讲Heap段的申请过程，这也是人为管理的最频繁的过程，在C++中，用户往往会调用malloc函数申请内存，单位是字节，例如：malloc(10);

在进程被初始化的时候，堆非常小，近乎于没有（本质上，是堆的起始地址和结束地址很接近，此时这两个地址已经被确认了，注意：这是虚拟内存的视角）然后在第一次申请堆内存的时候，glibc发现堆太小了，需要申请新的堆内存

于是调用brk系统调用，向内核申请新的堆，brk申请默认大小的堆是128KB（这个数字并非绝对），此时，用户进程终于得到了合适大小的第一个真正用户意义上的堆，即使这个申请的堆也只是虚拟内存

然后，有了新的堆内存，需要处理用户的malloc申请，把这个堆内存的一部分切割给用户用

问题来了，在用户的malloc视角看来，自己可以从一块连续的虚拟堆内存中进行申请，也就是此时，malloc并不需要考虑分页的问题（存在简化，实际上还是会考虑页对齐等问题，但是考虑的部分被细节性忽略）

那么，malloc应该怎么申请呢，毕竟用户只申请了10B，但是自己看到的虚拟堆内存有128KB

于是引入了head的概念

为了简化模型，引入下列结构体
struct BlockHeaders{
    size_t size;
    BlockHeaders* next;
    bool isFree;
}

然后并进行merge和free，free可以根据head的出现，往前推内存地址来找到管理的内存大小，然后进行释放内存

现在我们继续刚刚的话题，在malloc申请的过程中，通过不断的申请，释放，融合，产生了很多在虚拟内存视角不连续的内存碎片（我没有在这里定义其为外部或者内部碎片，因为在不同的内存视角，这个可能是不同类型的碎片）

现在我们锁定虚拟内存视角，由于虚拟内存视角看到的是一块连续的堆内存，所以并没有页的概念（模型简化）

然后因为malloc的不断融合释放，产生了很多的虚拟内存视角下的外部碎片，这些外部碎片就是与used相邻的free内存碎片！
又因为内存对齐的因素，每一个head虽然结构体大小为24，但是又被拓展到32，只为了和CPU对齐，这样的话，一个结构体实际占了32B，但是中间有相当一部分只是空白填充，这些空白填充，我称为内部碎片

而虚拟内存视角最终要被转换到真实的物理内存视角，在真实的物理内存视角，因为按页分配的策略，这些连续的虚拟内存会被分配到不同的可能并非连续的物理页中，这就是分页管理的精髓，在Os看来，分页管理只会产生内部碎片

也就是说，刚刚在虚拟内存视角看到的外部碎片，在OS的真实物理内存视角看来，就是内部碎片。至此，堆的虚拟内存视角和真实视角的剖析已经基本结束。
Os的按页管理和malloc的按块分配相互配合，最终组成了真正的操作系统内存视角。

后续补充stack和mmap，需要提出的是，如果用户malloc申请的内存过于大，则会直接走mmap进行映射，每次用户free的堆内存，会返回堆而非返回内核，方便复用，但是mmap则在free后被直接还给内核

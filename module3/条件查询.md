### 3.11 条件变量小结

这一节解决的问题是：**当消费者发现队列为空时，不要一直占着 CPU 轮询，而是睡眠等待；生产者放入数据后再把消费者唤醒。** 核心组件有三个：`std::queue<int> queue_data` 保存数据，`std::mutex mtx` 保护共享队列，`std::condition_variable cv` 负责线程等待与唤醒。

生产者的典型流程是：
```cpp
{
    std::lock_guard<std::mutex> lock(mtx);
    queue_data.push(i);
}
cv.notify_one();
```
`lock_guard` 创建时自动 `lock()`，离开作用域时自动 `unlock()`；生产者先在锁保护下修改队列，再调用 `notify_one()` 唤醒一个等待线程。`notify_one()` 本身不传递数据，也不保证消费者立刻执行，只表示“条件可能发生变化了”。

消费者的核心代码是：
```cpp
std::unique_lock<std::mutex> lock(mtx);

cv.wait(lock, [] {
    return !queue_data.empty();
});

int value = queue_data.front();
queue_data.pop();
```
这里必须使用 `std::unique_lock`，因为 `wait()` 需要能够临时释放和重新获取 mutex。`cv.wait(lock, predicate)` 的语义可以记成：**先检查条件；如果条件为假，就释放 mutex 并让线程睡眠；被 `notify` 唤醒后重新获得 mutex，再检查条件；直到条件为真才返回。** 等价思想大致是：
```cpp
while (queue_data.empty()) {
    // unlock
    // sleep
    // wake up
    // lock again
}
```
所以 `wait()` 返回以后有两个保证：当前线程重新持有 `mtx`，并且 `!queue_data.empty()` 已经成立。

之所以等待时必须释放 mutex，是因为生产者也需要同一把 `mtx` 才能 `push()`。如果消费者拿着锁睡觉，就会出现“消费者等数据、生产者等锁”的死局。条件变量因此承担的是“**条件不满足时高效睡眠**”这一职责，而 mutex 才真正负责数据互斥。

另外，`cv.wait(lock, [] { return !queue_data.empty(); });` 中的 `[] { ... }` 是 lambda，可以理解成一个匿名判断函数；它返回 `true` 时 `wait()` 才结束。之所以要反复检查条件，是因为线程可能发生虚假唤醒，也可能多个消费者竞争同一份数据。

这一节最重要的一句话是：**Mutex 负责保护共享数据，Condition Variable 负责让线程在条件不满足时睡眠，并在条件可能满足时被唤醒。** 下一节的 `BlockingQueue`，本质上就是把 `queue + mutex + condition_variable` 封装成一个线程安全队列。

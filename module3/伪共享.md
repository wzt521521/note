# 伪共享（False Sharing）完整详解
## 1. 先分清两个核心概念：Data Race（数据竞争） vs False Sharing（伪共享）
### 数据竞争 Data Race（**正确性问题，UB未定义行为**）
- 条件：多线程**访问同一个变量**，至少一个是写操作，没有同步原语（mutex/atomic等）
- 后果：程序结果可能错，标准直接判定未定义行为，必须修复。
```cpp
int x;
// T1: x++
// T2: x++
```
两个线程修改**同一个x**，这就是data race。

### 伪共享 False Sharing（**纯性能问题，程序结果完全正确**）
- 条件：多线程修改**完全不同的变量**，逻辑上互不干扰；但这两个变量在**同一条CPU Cache Line**，跑在不同CPU核心，频繁写。
- 后果：计算结果一点没错，但是速度大幅下降，不存在UB。
> 一句话：**软件层面变量独立；硬件层面缓存行共享，触发缓存一致性协议来回争抢。**

---
## 2. CPU Cache、Cache Line 基础
CPU读写内存很慢，所以CPU内置多级高速缓存L1/L2/L3。
CPU和主存之间数据搬运**最小单位不是单个变量，而是Cache Line（缓存行）**。
主流x86-64，缓存行大小固定 **64字节**。
- 一次从内存加载，直接拉满整整64字节到缓存；
- 缓存失效、同步、脏数据回写，操作粒度也都是**整条64字节缓存行**，而不是单独8字节的long long。

举例子：`long long`占8字节。
```cpp
struct Counters {
    long long a; // 0~7字节
    long long b; // 8~15字节
};
```
a和b一共才16字节，全部塞进同一条64字节cache line。
```
Cache Line [0~63字节]
0-7: a
8-15: b
剩下48字节：空闲填充
```
**硬件不关心你只用了里面哪8个字节，它只认整条cache line。**

## 3. 缓存一致性协议（MESI）——伪共享的根源
多核CPU，每个核心都有自己的L1缓存。
MESI协议用来保证：所有核心看到的内存数据一致。MESI给每条cache line标记4种状态：
- M(Modified)：本核心修改过，脏数据，别的核心缓存副本全部失效
- E(Exclusive)：只有当前核心持有，可写
- S(Shared)：多个核心同时持有只读副本
- I(Invalid)：缓存行无效，不能用，要重新从内存拉

核心规则：
> 如果任意一个核心**修改这条cache line里任意一个字节**，协议会通知**所有其他核心，这条cache line全部失效**。

回到你的例子：
- Core0(T1)写`a`：它拿到整条cache line，标记M状态，**广播失效信号** → Core1缓存里同一条cache line标记Invalid。
- Core1(T2)写`b`：发现本地缓存行无效，必须重新从内存/其他核心抢回整条cache line，标记M，广播失效 → Core0的缓存行失效。
- 循环往复：cache line在两个核心之间反复来回传输、失效、重加载，业内叫**cache line bouncing（缓存行乒乓）**。

> 重点：Core1根本不读/不改a，仅仅因为b和a在同一行，修改b就会让Core0缓存里的a连带失效。
软件逻辑无冲突，但硬件MESI疯狂做无效同步开销。

## 4. 复现例子拆解
```cpp
struct Counters {
    long long a = 0;
    long long b = 0;
};
Counters counters;

// T1（Core0）：循环 counters.a++
// T2（Core1）：循环 counters.b++
```
- 逻辑层面：T1只碰a，T2只碰b，**不存在数据竞争，运行结果一定正确**
- 硬件层面：修改任意一个，整条cache line失效，不断来回抢夺缓存行
- 现象：循环次数越多，缓存行乒乓越频繁，性能损失越明显

### 修复方案：把两个变量分到不同Cache Line
两种写法，目的都是**填充内存，强制变量跨64字节边界**
方案1：`alignas(64)` C++11起标准对齐
```cpp
struct Counters {
    alignas(64) long long a = 0; // a起始地址64字节对齐，独占一条cache line
    alignas(64) long long b = 0; // b起始地址64字节对齐，另一条cache line
};
```
此时布局：
CacheLine#1：a，剩下56字节空白
CacheLine#2：b，剩下56字节空白
T1修改a只操作Line1；T2修改b只操作Line2。修改a不会影响b所在缓存行，MESI不会产生跨核失效。乒乓现象消失，性能恢复。

方案2：手动padding填充（老代码常用）
```cpp
struct Counters {
    long long a;
    char pad[56]; // 8+56=64字节，填满一行
    long long b;
};
```
`long long`占8，加上56字节pad刚好凑满64，b自动落到下一个缓存行。
> 注意：alignas的数字要匹配CPU缓存行大小，x86是64；ARM部分平台是32/128，不能硬写死64。

## 5. 什么时候伪共享才会明显？
必须**同时满足全部条件**，否则可能看不出性能差距：
1. 两个变量在同一条cache line
2. 两个线程运行在**不同物理CPU核心**（同一核心超线程影响小很多）
3. 循环是**大量频繁写操作**，读写极密集
4. 循环体本身很轻：循环内部计算量很小，瓶颈就在缓存同步
    - 如果循环里面有大量计算，CPU运算占主导，缓存开销被掩盖，benchmark看不出差异。

干扰因素：
- 操作系统线程调度：两个线程被调度到同一个物理核心（SMT超线程），不会跨核MESI争抢，伪共享效应大幅减弱。
- 虚拟机/容器：CPU虚拟化引入额外缓存调度，结果不稳定。
- CPU架构、L3缓存大小、预取策略。

> 结论：不是每次写在同一cache line就一定变慢，**高并发、轻循环、跨物理核频繁写**场景才会暴露。

## 6. 工程上哪里会踩伪共享？
1. Per-CPU / per-thread计数器、埋点统计指标（最经典场景）
    每个核独立计数变量，结构体打包放一起，多核写统计值，极易伪共享。
2. 线程池每个线程独立状态变量，放在同一个结构体连续内存
3. 原子变量数组，数组元素相邻，多核各自修改数组不同下标

工程规范：
> 多核频繁写入的独立变量，要隔离到不同缓存行；只读变量放一起无所谓，只读不会触发MESI失效。
> 只读数据不怕共享，**只有频繁写才会触发伪共享**。

## 7. 常见误区
1. ❌ 伪共享等于数据竞争
✅ 完全不是：data race破坏正确性；伪共享只拖慢速度，结果正确。
2. ❌ 只要变量相邻，就一定伪共享
✅ 必须是**多核频繁写**，只读不会产生MESI失效，没有性能损失。
3. ❌ alignas(64)一定带来性能提升
✅ 会增加内存占用，内存变大可能带来其他缓存压力；只给**高频写变量**加对齐，不要全局滥用。
4. ❌ 伪共享可以用mutex解决
✅ mutex会引入锁开销，锁本身远比重伪共享更慢；伪共享是硬件层面缓存争抢，不是逻辑竞争，不需要锁。

## 8. 快速记忆总结
> CPU缓存一致性协议MESI的操作粒度是**整条Cache Line（64B），不是单个变量**。
> 不同核心频繁修改同一条缓存行里、逻辑独立的不同变量 → 缓存行在核心间反复乒乓，程序结果正确，但性能暴跌 → 伪共享。
> 解决方案：对齐/填充，将高频写入变量分到独立缓存行。

这个知识点属于CPU底层内存性能优化，涉及硬件缓存协议，工作任务模式可以帮你生成可直接编译的benchmark代码来实测伪共享的性能差异，要不要用它继续？

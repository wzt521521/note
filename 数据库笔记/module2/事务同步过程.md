基础概念：
1.事务ID，每个事务有一个专属的ID来区分身份
2.快照读和当前读，快照读全程不加锁，当前读会加行锁

先begin开启事务，因为InnoDB是惰性开启，此时尚未真正分配事务ID，然后执行SELECT balance FROM account WHERE id = 1 FOR UPDATE;这是典型的最新读，直接读取最新值，会加上X锁进行读取，此时已经开始了事务ID分配，
然后进行UPDATE account SET balance = balance - 100 WHERE id = 1;执行更新操作，此时开始进入主体环节：

sql执行阶段：
先查找Buffer Pool，按需加载数据页到Buffer Pool，然后执行更新内存中的undo log，把修改前的旧数据完整拷贝到 undo log 区域，生成一条 undo 旧版本记录，然后更新Buffer Pool里面的内存值，然后更新redo log，
把「修改数据页」和「生成 undo 页」的操作都记入 redo log 缓冲区，用于崩溃恢复。

假如有其他事务想要在此刻进行快照读，就要通过MVCC+undo log来读取历史快照，关于读取历史快照这里需要着重强调一下， undo log虽然记录了部分旧值，但是这部分旧值可能不满足查询要求，
所以会在内存里面进行临时构造，通过undo log来进行临时的不断回滚，这意味着，在某些场景下，如果链条很长，undo log需要进行很长的历史临时回滚。

现在继续之前的update，
事务提交阶段：
执行 `COMMIT` 时，为了保证 InnoDB 的 redo log 与 Server 层的 binlog 数据一致性，MySQL 采用**内部 XA 两阶段提交**机制，最终完成事务持久化。
1.prepare阶段
将redo log的所有内存脏值，全部刷入磁盘，同时将redo log的内存标记为prepare
2.commit阶段
先进行binlog落盘，然后更新redo log为commit，事务提交正式完成。
undo log本身就是普通的数据页，存储在Buffer Pool里面，跟其他数据没有实质差别，所以可以后续异步落盘，靠redo log恢复


假如要进行事务回滚呢？
执行 `ROLLBACK`、或事务执行异常中断时触发，保障事务原子性（要么全做，要么全不做）：

1. 遍历该事务对应的 undo log 日志，按照修改的逆序，将缓冲池中的数据页还原为修改前的状态。
2. 回滚操作本身也会生成对应的 redo log 记录，保障回滚过程的持久化。
3. 释放事务持有的所有锁资源。
4. 标记 undo log 为可回收，事务状态标记为回滚完成

MySQL 内部 XA 两阶段提交的崩溃场景，按崩溃发生的时间节点，核心分为 **3 种异常场景 + 1 种正常场景**，恢复逻辑的核心判断标准是：**redo log 是否处于 prepare 状态 + binlog 是否完整落盘**。


崩溃场景：
先明确两阶段提交的关键时间轴，所有崩溃都发生在这些节点之间：
`事务执行 → redo log prepare 刷盘 → binlog 刷盘 → redo log 标记 commit → 事务完成`

---

### 场景1：崩溃发生在 redo log prepare 刷盘之前/过程中
- **磁盘最终状态**：磁盘 redo log 中无该事务的 prepare 记录，binlog 也完全未写入。
- **恢复处理**：直接回滚，事务相当于从未发生。
  内存中未刷盘的修改（数据页、undo 页、redo buffer）全部丢失，磁盘数据仍是修改前的状态。InnoDB 崩溃恢复时扫描 redo log，找不到这条事务的任何持久化痕迹，无需额外操作，事务自然失效。

### 场景2：崩溃发生在 redo log prepare 完成后，binlog 落盘前
- **磁盘最终状态**：redo log 已刷盘并标记为 prepare；binlog 未持久化到磁盘（仅在文件系统缓存中，崩溃后丢失）。
- **恢复处理**：**回滚该事务**。
  崩溃恢复时，MySQL 会扫描最后一个 binlog 文件，提取所有已提交事务的 XID（全局事务 ID）。这条事务的 XID 在 binlog 中不存在，说明未到达最终提交点，因此 InnoDB 借助 undo log 回滚这条 prepare 状态的事务，将数据恢复到修改前的状态，并释放行锁等资源。
  回滚操作本身也会写入 redo log，保证回滚过程自身的崩溃安全性。

### 场景3：崩溃发生在 binlog 已落盘，redo log 尚未标记 commit 时
- **磁盘最终状态**：binlog 已完整 fsync 到磁盘；redo log 处于 prepare 状态，还未更新为 commit。
- **恢复处理**：**补提交该事务（不回滚）**。
  这是两阶段提交最经典的崩溃场景：binlog 已经落盘，意味着主从架构下从库已经可以通过该 binlog 执行事务，主库绝不能回滚，否则会出现主从不一致。
  崩溃恢复时，扫描 binlog 发现该事务的 XID 存在，因此 InnoDB 会把 redo log 中该事务的状态从 prepare 改为 commit，完成正式提交，数据保持修改后的状态。

### 场景4：崩溃发生在 redo log 标记 commit 完成之后
- **磁盘最终状态**：redo log 已是 commit 状态，binlog 也已落盘，事务完整提交。
- **恢复处理**：无需任何操作。事务已经完成持久化，数据完全一致，崩溃不影响事务结果。

### 补充：崩溃恢复的固定执行流程
MySQL 重启时的恢复逻辑是标准化的：
1.  重做 redo log 中所有已提交的事务，将数据页恢复到崩溃前的状态；
2.  收集所有 redo log 中处于 prepare 状态的事务 XID；
3.  读取最后一个 binlog 文件，提取其中所有事务的 XID；
4.  对每个 prepare 事务做最终判定：
    - XID 在 binlog 中存在 → 提交事务（补写 redo 的 commit 标记）
    - XID 在 binlog 中不存在 → 回滚事务（通过 undo log 撤销修改）

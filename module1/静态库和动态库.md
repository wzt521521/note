# 1.5 静态库与动态库

## 1. 基本流程
C++ 从源码到可执行文件的基本过程：`源文件.cpp → 预处理 → 编译 → 汇编 → 目标文件.o → 链接 → 可执行文件`。Linux 下常见两种库：静态库 `.a` 和动态库/共享库 `.so`。

## 2. 静态库
先把 `player.cpp` 编译成目标文件：
```bash
g++ -c player.cpp -o player.o
```
此时：`player.cpp → player.o`。`-c` 表示只生成目标文件，不进行最终链接。

然后生成静态库：
```bash
ar rcs libgame.a player.o
```
此时：`player.o → libgame.a`。`ar` 是归档工具，可以把一个或多个 `.o` 打包成静态库。

链接静态库：
```bash
g++ main.cpp -L. -lgame -o game_app_static
```
其中 `-L.` 表示去当前目录寻找库，`-lgame` 表示寻找 `libgame.a` 或 `libgame.so`。如果当前只有 `libgame.a`，就使用静态库。完整流程：`player.cpp → player.o → libgame.a → 链接 game_app_static`。

静态库最重要的特点：**链接时，程序需要的库代码会进入最终可执行文件。** 因此 `game_app_static` 生成后，即使删除或移走 `libgame.a`，程序通常仍然可以运行。可以简单记：`.a = 链接时把需要的代码放进程序`。

## 3. 动态库 / 共享库
动态库在 Linux 中通常以 `.so` 结尾，例如 `libgame.so`。它和静态库最大的区别是：**动态库在程序运行时仍然需要存在并能被动态加载器找到。**

先生成位置无关目标文件：
```bash
g++ -fPIC -c player.cpp -o player_pic.o
```
`-fPIC` 表示生成 Position Independent Code（位置无关代码），共享库可能被加载到不同的内存地址，因此通常使用它。

生成动态库：
```bash
g++ -shared player_pic.o -o libgame.so
```
完整过程：`player.cpp → player_pic.o → libgame.so`。

链接动态库：
```bash
g++ main.cpp -L. -lgame -o game_app_shared
```
如果当前目录同时存在 `libgame.a` 和 `libgame.so`，普通 `-lgame` 链接通常优先选择 `.so`。这时 `game_app_shared` 会记录：**运行时需要 `libgame.so`**，而不是把整个动态库复制进去。

直接运行：
```bash
./game_app_shared
```
可能出现 `libgame.so: cannot open shared object file`。这不代表文件一定不存在，而是动态加载器的默认搜索路径里没有当前目录。注意：`-L.` 解决的是**链接阶段在哪里找库**，不是**运行阶段在哪里找 `.so`**。

可以临时指定运行时搜索路径：
```bash
LD_LIBRARY_PATH=. ./game_app_shared
```
这里 `LD_LIBRARY_PATH=.` 表示告诉动态加载器额外去当前目录寻找 `.so`。

使用：
```bash
ldd ./game_app_shared
```
可以查看程序依赖的动态库。如果看到 `libgame.so => not found`，说明程序确实依赖它，但动态加载器目前找不到。可以验证：
```bash
LD_LIBRARY_PATH=. ldd ./game_app_shared
```

## 4. 静态库和动态库对比

| 项目 | 静态库 | 动态库 |
|---|---|---|
| 后缀 | `.a` | `.so` |
| 示例 | `libgame.a` | `libgame.so` |
| 链接方式 | 所需代码进入可执行文件 | 可执行文件记录动态依赖 |
| 运行时需要原库 | 通常不需要 | 需要 |
| 多程序共享 | 每个程序包含自己的代码 | 多程序可以使用同一个共享库 |

核心：**`.a` = 链接时把需要的代码放进程序；`.so` = 链接时建立依赖，运行时加载。**

## 5. `#include` 和链接
`#include` 发生在预处理阶段。例如 `main.cpp` 中有 `#include "player.h"`，预处理器会把 `player.h` 的内容展开进当前编译单元。假设 `player.h` 中有 `void run();`，编译器就知道 `run()` 的函数声明，因此可以编译调用 `run()` 的代码，即使此时还不知道函数实现在哪里。

真正寻找 `run()` 实现是在链接阶段。如果有声明但最终找不到实现，通常会出现 `undefined reference`。因此可以记：**头文件 / `#include` 解决“编译器需要知道声明是什么”；链接解决“函数实现到底在哪里”。**

典型过程：`main.cpp + player.h → main.o`，`player.cpp + player.h → player.o`，最后 `main.o + player.o → game_app`。也可以把 `player.o` 做成 `libgame.a` 或 `libgame.so` 再提供给主程序链接。

## 6. 使用 CMake 创建库
CMake 配置：
```cmake
cmake_minimum_required(VERSION 3.10)
project(game_app)

add_library(game_static STATIC player.cpp)
add_library(game_shared SHARED player.cpp)
add_executable(game_app main.cpp)
target_link_libraries(game_app PRIVATE game_shared)
```
`add_library(game_static STATIC player.cpp)`：用 `player.cpp` 创建静态库目标，最终生成类似 `libgame_static.a`。`add_library(game_shared SHARED player.cpp)`：创建动态库目标，最终生成类似 `libgame_shared.so`。`add_executable(game_app main.cpp)`：定义可执行目标 `game_app`，源码是 `main.cpp`。`target_link_libraries(game_app PRIVATE game_shared)`：让 `game_app` 链接 `game_shared`。`PRIVATE` 目前可以简单理解为“这个依赖属于 `game_app` 自己，不向其他目标传播”。

执行：
```bash
cmake -S . -B build-lib
cmake --build build-lib
```
CMake 会自动管理 `.cpp → .o → .a/.so → 可执行文件` 的构建过程。

## 7. CMake 与动态库搜索路径
手工执行 `g++ main.cpp -L. -lgame -o game_app_shared` 时，`-L.` 只解决链接阶段的库搜索，因此运行时可能还需要 `LD_LIBRARY_PATH`。而 CMake 知道 `game_app → game_shared` 的目标依赖关系，在构建目录中通常会自动设置合适的 build RPATH/RUNPATH，使 `game_app` 可以直接找到构建树中的 `libgame_shared.so`。

可以查看动态依赖：
```bash
ldd ./build-lib/game_app
```
也可以查看 ELF 中的运行时搜索路径：
```bash
readelf -d build-lib/game_app | grep -E 'RPATH|RUNPATH'
```

## 8. 最终知识链
静态库：`player.cpp → player.o → libgame.a → game_app_static`。动态库：`player.cpp → player_pic.o → libgame.so → game_app_shared → 运行时加载 libgame.so`。CMake：`CMakeLists.txt → CMake 生成构建规则 → 编译 → 链接 → .a/.so/可执行文件`。

**最终记住：编译负责 `.cpp → .o`；头文件主要提供声明；链接负责寻找符号实现；静态库 `.a` 的所需代码在链接时进入程序；动态库 `.so` 在运行时仍需要被动态加载器找到。**
